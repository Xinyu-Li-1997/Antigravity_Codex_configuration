# Codex 与反重力工程和科研协作实践

本指南说明 `user-guard` 与共享 `cae-harness` 技能的任务分工、输入预算、回执核验及 Windows／WSL 同步方式。具体命令见[共享技能](../template/user-guard/skills/cae-harness/SKILL.md)，安装入口见[仓库说明](../README.md)。

## 项目主责与任务交接

| 项目侧重 | 总控 | 独立协作职责 |
| --- | --- | --- |
| 代码工程 | Codex | 反重力校正方向、润色技术表述并独立验收 |
| 科研主题 | 反重力 | Codex 完成其中部分高质量编码和数学工作 |

主责按用户确定的项目或阶段安排。总控拆分独立任务，核实返回的原始证据并组织交付。方法选择、物理假设和适用范围仍按用户的裁决推进。

两种方向共用同一套脚本与结果格式。派工任务单须写清用户最新定论、输入基线、工作目录、允许改动的文件范围、交付形式和验收命令；由于跨端调用运行在独立的无头 CLI 进程中，它看不到主桌面会话里的聊天上下文与外部插件连接器，所需背景信息均应通过任务单明确传入。

## 交互模型与后台任务选路

桌面端和 IDE 主会话优先采用用户显式选择的模型和挡位。`cae-harness` 根据模型目录为自己启动的 CLI 子任务选路。Codex 原生 `spawn_agent` 由主线程根据当前可用模型和挡位显式调度。

| 任务 | 自动选路依据与挡位 |
| --- | --- |
| 数理推导、路线论证、高阶数值格式、守恒性、稳定性及并发根因复核 | 优先采用深度推理模型与可用的单模型最高挡（如 `max` 或 `xhigh`）。后台默认避开内部自动派生挡 `ultra` |
| 常规编码、审查、审计、验收命令首轮及长篇技术润色 | 按输入规模选择工程模型，采用 `high`。复杂问题和验收失败后的排查可升至单模型最高挡 |
| 短篇纯文字润色、表面格式或拼写核查 | 分别采用 `medium` 和 `low`，轻量核查可选轻量模型 |

自动策略默认排除固定复合模式、自动路由配置和占用长周期稀缺配额的内置第三方模型。反重力 Orchestrator 的固定多模型交替与 Codex `ultra` 的自动委派并非同一机制，完整层级和维护矩阵见[总 README](../README.md)。显式选路可用 `--engine <后端>:<模型名或别名>` 和 `--tier`。回执记录选定模型、挡位和选路依据。

`probe` 默认仅读取静态环境信息与本地模型缓存；`probe --discover-models` 调用 `agy models` 查询反重力模型目录并刷新缓存。`assess` 以只读方式报告程序路径、模型目录来源与采集时效、声明的上下文与挡位、未知项及场景选路建议（加 `--discover-models` 亦不写缓存），不凭缓存宣称模型实际性能。当前认证、实际可用性与任务表现需要对应 CLI 的受控运行证据。一份运行回执的结论限于其版本、环境和输入。

两端的 CLI 调用各自使用对应工具的认证和计费配置。日常按既定分工自动按需发起协作以降低人工调度成本；一旦某一方返回额度或用量上限，`cae-harness` 立即终止同批后续请求、返回 `quota_exhausted`（退出码 `5`），并将解析出的恢复时间写入本侧运行缓存（按执行侧区分的额度状态文件，兼容旧 `cae_quota_state.json`）。冷却期内再次触发调用时，脚本在真正发请求前自动拦截（`preflight_blocked: true`），由当前总控提示用户选择先不发起（改由本侧直接完成）或在充值／恢复后附带 `--retry-quota` 重试（获准的新重试批次成功且未产生新熔断时才清理旧记录）。本机制仅调用用户在本地通过官方渠道安装并登录的 `agy` 与 `codex` CLI，不接入其他命令行工具、非官方第三方接口或外部 SDK。

### 会话列表与项目树隔离

- **反重力调用 Codex**使用 `codex exec --ephemeral --skip-git-repo-check -C <目标目录>`，以临时会话执行。
- **Codex 调用反重力**使用 `agy` 无头模式，其会话使用独立 CLI 存储 `~/.gemini/antigravity-cli`。
- 发起方总控汇总分片审计与结构化协作的结论、文件行号和变更报告。

## 上下文容量与覆盖范围

| 信息 | 能够说明的内容 |
| --- | --- |
| 本地窗口配置 | 用户或客户端配置的目标容量 |
| 模型缓存中的容量 | 缓存记录的模型元数据，需结合版本和配置解释 |
| 输入预算 | 为安排任务而使用的估算，来源和预留策略随回执披露 |
| 真实执行证据 | 本次实际读取范围、输出、压缩情况和失败信息 |

窗口策略按用户裁定执行：先确定实际运行侧和具体模型，使用该模型自身声明的最大窗口；最大值未知时用该模型已知默认值。若 Codex 连默认值也未知且存在宿主全局窗口覆盖，则阻止启动并提示刷新目录，避免错误继承。不能以主会话窗口或另一侧缓存替代。Codex 本次窗口参数须与计划一致，反重力的规划预算不能解释为宿主窗口设置。

源码字节数只能用于初步估算。工具输出、系统指令、JSON Schema、推理和最终答案也占用上下文。`--codex-input-budget` 和 `--agy-input-budget` 允许按任务调整估算预算，默认策略值随探测结果说明。

`single-pass` 将预算允许的文件安排在一个审计任务中，旧 `whole-1m` 参数作为兼容别名处理。完整读取与无压缩分析需要本次执行证据确认。遇到超出预算、不可读或被跳过的文件，总控检查清单和原因，再确定补充任务。

分片审计保留每片的文件范围。跨模块全局变量、边界通量、雅可比耦合或符号约定可能横跨多个分片。例如审查间断伽辽金谱元法（DGSEM）的离散守恒性时，总控应联合核对体积分、界面数值通量与离散度量项。单片结论的适用范围以实际输入为准。

## 只读协作与代码实现

| 入口或角色 | 用途 |
| --- | --- |
| `readonly-reader` | 长文件通读和精确摘录 |
| `readonly-auditor`／`audit` | 文件、公式、数字和审计发现的核验 |
| `readonly-collaborator`／`task` 的只读类型 | 方向建议、润色文本、数学推导及一般复核 |
| `task --kind code` | 明确范围的代码实现及可选验证 |
| `gate` | 修改后执行指定验收命令，按限定轮次修复 |

反重力只读角色开放读取、检索和结构化回执接口（`[read_file, search_web, finish]`）。Codex 的只读 CLI 调用使用 `-s read-only`。Codex 原生只读角色依其角色指令和继承的宿主权限运行。执行前后比较工作区文件状态，发现写入时如实报告。

代码任务用 `--write-scope` 描述允许写入的文件，可重复指定。执行后核对真实变更集，越界报告由总控处理。这项检查发生在写入之后，调用方须为异常情况保留实际差异并检查原有未提交修改。若门禁无法读取目录或文件快照，会明确标注范围未验证，保留已执行轮次及调用证据，停止验收和后续写入轮次。

### 双侧项目目录硬边界约束

任何项目除用户明确下达指令批准外，反重力与 Codex 均严禁在当前项目根目录之外的业务目录或宿主机全局配置中创建、修改、移动或删除任何文件或目录（包括严禁向父目录或外部路径创建 `.codex-worktrees`／`git worktree`、改动其他项目目录或擅改宿主机全局配置；系统标准临时目录、宿主与项目关联的对话记忆／子代理轨迹／制品草稿目录及标准 `.cache` 工具缓存区正常放行）：
- **反重力侧**由 `PreToolUse` 钩子（`status_guard.py`）根据可解析的 Python AST 与 Shell 命令检查潜在越界写入。交互主会话可返回 `force_ask`，提示当前任务意图、动作、目标路径和触发语句。无头子任务（`CAE_HARNESS_DEPTH=1`）对识别到的越界调用返回 `deny`。
- **Codex 侧**安装器默认将缺失或 `danger-full-access` 的沙箱设置改为 `workspace-write`；`approval_policy = "on-request"` 及工作区沙箱网络访问只补缺失项，保留已有值。显式 `--no-sandbox-config` 可跳过这些配置。`cae-harness` 的 CLI 子任务显式使用 `-s read-only|workspace-write -c approval_policy="never"`。实际文件权限取决于生效的宿主沙箱和操作系统。

验收命令由任务明确给出。编译成功、守恒残差、网格收敛、时间步收敛和物理模型验证分别有自身判据，使用与问题定义相符的检查和容差。

## 进度、失败与取消

标准错误流提供生命周期事件，标准输出提供最终 JSON。父会话保留自己启动的进程句柄，使用事件观察进度，并等待最终状态。

成功、部分完成、输出无效、超时和失败分别处理。返回内容需要满足对应结构，执行器失败与验收结果均进入判断。总控检查回执中的已完成范围、错误原因和工作区差异后决定补做事项。

取消与超时处理针对本次派生的进程树。任务完成后，最终结论仍需总控核对。跨程序独立调用的进程状态与现有桌面对话的状态分别由各自宿主管理。

## 生命周期恢复与后台计算

反重力 App、IDE 和 CLI 使用本侧用户级插件目录。Windows 与 WSL 的用户配置和会话目录各自管理，插件源码从同一提交安装。

两端按 `R9` 利用可读轨迹恢复用户原话，对照摘要和文件状态，汇报已完成与待交付事项。进入收口时，在既有授权内完成局部工作，整理实测进展、待办事项与新会话提示词。

- 反重力在 `SessionStart` 和 `PreInvocation` 检查轨迹，达到相应条件时进入提醒、排空或冻结。`Stop` 校验交接材料，并按反重力协议处理 `/goal` 交接标记。
- Codex 在 `SessionStart` 的 `compact` 或 `resume` 来源恢复原话。交接钩子默认采用 `advisory`（仅观测提醒，压缩次数阈值默认 `0`，不套用反重力侧阈值）。显式启用 `enforce` 前，须明确触发策略并在目标宿主完成受控验证。严格模式通过 `Stop` 处理交接续跑及当前回合的结束，目标和后台任务另由 Codex 宿主管理。

事件、阈值和归档方式见[生命周期钩子规范](架构设计与生命周期钩子规范.md)。

长耗时数值任务按本机资源约束在 WSL 或独立计算环境执行。总控统一安排共享计算资源和写入范围，按运行宿主提供的后台完成通知或进度事件继续工作。重复状态查询与同质回复由现有钩子检查。

## Windows 与 WSL 版本同步

1. 记录待验证的 Git 基线与工作区差异。独立复核使用同一份源码及实际测试结果。
2. Windows 和 WSL 分别在临时目录运行安装器：单端验证可用 `--app antigravity --target-dir <临时插件目录> --no-zotero` 或 `--app codex --codex-home <临时Codex目录> --no-zotero`；双端联合验证可同时传入两者。
3. 两侧运行离线回归，核对脚本与技能内容一致，检查本侧 Python 命令、CLI 路径及参数。真实调用测试另行记录运行版本、模型、输入和回执。
4. 当前任务进入合适间隙后，从已验收提交更新各侧用户目录。Codex 技能安装与反重力插件安装共享同一份源码，配置和认证按对应运行环境解析。

WSL 优先选择本侧已登录的原生 CLI。具备互操作条件时，可回退到 Windows 侧 CLI。使用 Windows CLI 处理 WSL 项目时，`/mnt/<盘符>` 共享目录可用于授权写入。WSL 纯 Linux 路径的只读任务可使用 Windows 临时镜像，代码写入须改用共享目录或已登录的 WSL 原生 CLI。以实际探测和对应方向的执行回执确认可用范围。

遇到网络、认证或模型访问错误时，保留对应错误状态和来源，再定位本侧配置。环境诊断与业务任务的代码修改分别按本次授权范围处理。

官方接口可查阅 [Codex 非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode)、[Codex 技能](https://learn.chatgpt.com/docs/build-skills)和[反重力无头模式](https://antigravity.google/docs/cli/headless)。

运行侧回退发生在业务执行之前：程序缺失时按已探测互操作能力选择另一侧；反重力还可在 `agy models` 预检确认未登录后回退。业务调用一旦启动，失败只报告原结果，不自动换端重做写入。
