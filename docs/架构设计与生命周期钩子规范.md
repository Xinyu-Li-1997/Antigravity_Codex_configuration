# `user-guard` 架构设计与生命周期钩子规范

本文记录反重力与 Codex 的事件适配、状态迁移、交接响应和证据边界。实际支持范围以对应宿主版本和运行回执为准。部署与协作流程见[仓库说明](../README.md)与[协作实践指南](反重力全域工程化最佳实践指南.md)。

---

## 一、 Antigravity 钩子协议规范与编排总览

反重力插件将 `hooks.json` 放在插件根目录，注册同步命令钩子（`type: "command"`）。本插件按相对于插件根目录的路径启动钩子，从 `stdin` 读取 **camelCase** 格式载荷，在 `stdout` 输出单行 JSON 响应。宿主接口见[反重力钩子文档](https://antigravity.google/docs/hooks)。

插件运行时，宿主自动向钩子子进程注入两个关键环境变量：
- `PLUGIN_ROOT`：插件代码安装目录（如 `~/.gemini/config/plugins/user-guard`）；
- `PLUGIN_DATA`：插件专属持久化运行数据目录（如 `~/.gemini/antigravity/plugin_data/user-guard`）。

`user-guard` 优先将状态（`state/`）与诊断日志（`logs/`）写入 `PLUGIN_DATA`，使运行数据与插件源码分离。

### `hooks.json` 标准编排结构

```json
{
  "user-guard-lifecycle": {
    "SessionStart": [
      {
        "type": "command",
        "command": "python3 -X utf8 -I -B ./hooks/session_context_loader.py --event SessionStart",
        "timeout": 30
      }
    ],
    "PreInvocation": [
      {
        "type": "command",
        "command": "python3 -X utf8 -I -B ./hooks/session_context_loader.py --event PreInvocation",
        "timeout": 30
      }
    ],
    "PreToolUse": [
      {
        "matcher": "^(?:run_command|read_file|manage_task|write_file|edit_file|invoke_subagent|define_subagent|send_message|swarm|schedule|browser_.*)$",
        "hooks": [
          {
            "type": "command",
            "command": "python3 -X utf8 -I -B ./hooks/status_guard.py",
            "timeout": 15
          }
        ]
      }
    ],
    "Stop": [
      {
        "type": "command",
        "command": "python3 -X utf8 -I -B ./hooks/reply_repeat_guard.py",
        "timeout": 15
      }
    ]
  }
}
```

> **跨平台命令自适应**：`install.py` 在部署时会根据目标操作系统环境自动探测可用解释器（Windows 下优先探测 `python.exe` / `python` / `py -3`，Linux/macOS 下优先探测 `python3`），重写为对应平台的精确命令前缀。

## 二、 核心守护模块算法规范

### 1. 上下文压缩增量原话回溯 (`session_context_loader.py` + `user_words.py`)

#### （1）宿主事件机理与设计依据
反重力适配器用 `SessionStart` 处理会话启动，用 `PreInvocation` 扫描当前会话轨迹中新出现的 `"type": "CHECKPOINT"`。恢复提示经 `injectSteps` 注入。若宿主传入的 `transcriptPath` 指向 `transcript_full.jsonl`，`resolve_compact_transcript_path` 优先选取同目录的紧凑轨迹 `transcript.jsonl` 进行增量扫描与体积统计，遇到 `truncated_fields` 时按需回查完整轨迹。

#### （2）二进制字节游标增量状态机 (`<convId>_compaction.json`)
为按新检查点回读原话并减少重复扫描，引擎维护以下增量状态（`telemetryVersion = 3`）：
- `scannedByteOffset` 与 `scannedTranscriptName`：上次已扫描到的紧凑版 `transcript.jsonl` 字节偏移量及文件名（从旧版或 `transcript_full.jsonl` 切换升级时保留已注入检查点并重新标定遥测）；
- `latestCheckpointStep`：已观测到的最大 `CHECKPOINT` 步骤号（初始为 `-1`）；
- `lastInjectedCheckpointStep`：已完成原话注入的最大 `CHECKPOINT` 步骤号（初始为 `-1`）；
- `hasExplicitUserInput`：当前会话是否包含人类显式输入（自动排除纯子代理会话）。

每次触发时，仅以二进制模式 `seek(scannedByteOffset)` 扫描新增尾部字节：
1. **未压缩日常轮次**（`latestCheckpointStep == -1`）：更新游标并返回 `{"injectSteps": []}`；
2. **首次或新一轮压缩发生后首轮**（`latestCheckpointStep > lastInjectedCheckpointStep`）：
   - 解析 `transcript.jsonl`，遇到 `truncated_fields: ["content"]` 时，通过索引从可读的 `transcript_full.jsonl` 记录补全；
   - 使用外层标签边界定位（首 `<USER_REQUEST>` 配对元数据块前的末 `</USER_REQUEST>`）及紧随 `ask_question` 的 `GENERIC` 步骤解析，完整提取用户打字原话与交互选项回答；
   - 原子落盘完整档案 `<PLUGIN_DATA>/state/<convId>_user_words.md`；
   - 按预算上限（总长 `8000` 字符、单条 `1200` 字符，超限时必保首轮立项总纲与最近定论轮次）构造含归档文件绝对路径指针的 `systemMessage` 注入，并将 `lastInjectedCheckpointStep` 更新为 `latestCheckpointStep`；
3. **压缩后的后续日常轮次**（`latestCheckpointStep == lastInjectedCheckpointStep`）：返回 `{"injectSteps": []}`。

#### （3）Codex 侧多段 Rollout 压缩／恢复回溯模式（`--client codex`）
Codex 在触发上下文压缩或恢复会话时，向 `~/.codex/hooks.json` 中匹配 `^(compact|resume)$` 的 `SessionStart` 钩子传入 `session_id` 与当前 `transcript_path`（位于 `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`）。同一逻辑会话在多次续跑或归档后可能跨越多个 `rollout-*.jsonl` 分段（含 `archived_sessions/`）：
1. 引擎首先校验首行 `session_meta` 并排除 `subagent` 会话，再扫描合并同 `session_id` 的可读主会话分段；
2. 优先依据 `internal_chat_message_metadata_passthrough` 中的 `provenance.type` 过滤 `harness`／`agents_md` 系统注入块，保留人类输入与 `<send_user_message_question_reply>` 选项框回答，跨分段按稳定记录 ID 去重；
3. 原子写入 `~/.codex/hooks/state/user-words/<session_id>.md` 与 SHA-256 校验清单（若遇读取缺口且存在上次已验证文档则保留旧档并如实标注缺口），通过 `hookSpecificOutput.additionalContext` 返回归档路径与预算内核心原话摘要。

### 2. `PreToolUse` 项目目录硬边界与防空转轮询门禁 (`status_guard.py`)

#### （0）项目外文件改动检查（R4）

针对 `write_file`、`edit_file` 与 `run_command`，钩子从 `workspacePaths`（回退 `cwd`）取得项目根目录，检查可识别的外部业务路径和运行时缓存。实际权限边界由宿主沙箱和操作系统实施。
- **自动放行的合法运行时区域**：当前项目根目录（含 `<盘符>:/...` 与 `/mnt/<盘符>/...` 跨端挂载等价路径）、系统标准临时目录（`/tmp`、`%TEMP%`）、宿主与项目关联的对话记忆／子代理轨迹／制品草稿目录（`~/.gemini/antigravity/{brain,plugin_data,conversations,scratch,...}`、`~/.codex/{memories,sessions,cache,tmp,...}`）以及标准工具缓存区（`~/.cache/...`），同时对本地可达路径执行 `Path.resolve()` 防御软链接／目录联接越界逃逸；
- **AST 与子句命令头检查**。对 `python -c`／here-string／heredoc 中可解析的内联脚本，使用 Python `ast` 检查写删调用，例如带 `'w'|'a'|'x'|'+'` 的 `open`、`.write_text`、`os.remove`、`shutil.rmtree` 或 `shutil.copy*` 的目标端。外层 Shell 先剥离可识别的 `wsl`／`bash -lc`／`powershell -Command` 包装，再按子句匹配动作与路径。
- **真实越界处置与结构化可读提示**：检测到向项目外业务目录执行写删、创建外部 `git worktree`（如 `../.codex-worktrees`）或改写全局核心配置（如 `~/.gemini/config`、`~/.codex/config.toml`）时：
  - **交互主会话**（未设置 `CAE_HARNESS_DEPTH=1`）：返回 `{"decision": "force_ask", "reason": "..."}`，在 UI 弹窗按四要素清晰列出**当前任务意图（`toolSummary`）、具体写删动作、项目外目标路径与触发语句片段**，交由用户一目了然地审阅批准；
  - **跨端无头子任务**（`CAE_HARNESS_DEPTH=1`）对识别到的越界调用返回 `{"decision": "deny", "reason": "..."}`。

#### （1）严格锚定的证据文件识别
仅对以下目标启用指纹守卫，严禁误伤项目普通源码与业务 JSON 配置（如 `http_status.json`、`test_result.json`）：
- 扩展名属于 `.log`、`.out`、`.err`、`.output`；
- 文件名严格匹配锚定正则：`^(?:journal[^.]*\.jsonl|output\.[^.]+|task[-_]?output[^.]*(?:\.[^.]+)?|results?(?:\.(?:txt|json|jsonl|dat|csv))?|task\.(?:json|txt|status)|wf_[^.]+\.json)$`；
- 路径位于 `.system_generated/tasks/` 或 `.system_generated/steps/` 下（显式豁免插件自身的 `state/` 与 `logs/` 目录）。

#### （2）查询参数签名与快速复合指纹
- **查询键构造**：
  - `read_file` 使用 `read_file:<canonical_path>|s=<StartLine>:e=<EndLine>:b=<ByteOffset>` 作为查询键，以便区分文件的不同读取范围与同一页的重复查询。
  - `run_command`：剥离 `wsl`、`bash -c`、`powershell -Command`、`env`、`timeout` 等前导包装器后识别只读命令，键为 `run_command:<canonical_path>|<normalized_command>` —— 保证先 `grep` 后 `tail` 变参放行，同参原地轮询拦截；
  - `manage_task(Action="status")` 比对 `<brain>/<convId>/.system_generated/tasks/<TaskId>.log` 的文件指纹。检测到新日志时放行，缺少日志文件时使用 `30s` 冷却窗口。
- **跨子系统不可达路径豁免**：在 Windows 宿主下通过 `wsl` / `ssh` / `docker` 查看子系统内部宿主机不可见路径（如 `/home/.../run.log`）时自动放行，防止 `non_existent` 假指纹锁死。
- **复合文件指纹（防 GB 级算例日志超时）**：
  $$\text{Fingerprint} = \begin{cases} (\text{mtime\_ns},\ \text{size},\ \text{SHA256}_{\text{full}}), & \text{size} \le 4\ \text{MB} \\ (\text{mtime\_ns},\ \text{size},\ \text{SHA256}_{\text{head 1MB} \parallel \text{tail 1MB}}), & \text{size} > 4\ \text{MB} \end{cases}$$

### 3. `Stop` 防同质等待刷屏门禁 (`reply_repeat_guard.py`)

- **防死循环双保险**：
  1. 检查官方 `payload.get("continuationActive")`：若为 `true`（本轮已处于 `Stop` 钩子触发的强制续跑中），无条件返回 `{"decision": "allow"}`；
  2. 记录已拦截的归一化签名列表 `blockedSignatures`，同一签名在单回合内最多阻断 1 次。
- **保留数值进展的同质性判据**：
  - 优先定位紧凑版 `transcript.jsonl` 并从尾部 `256 KB` 窗口逆序定位最近一条 `USER_INPUT`（或子代理父消息）后的最新模型回复；当单回合轨迹超过 `256 KB` 时，自动按 `256 KB` 分块向前逆序溯源，精确锁定真实 `turn_<step>_<hash>`（避免多个长回合共享 `turn_0_initial`）；
  - 若回复长度 `<= 300` 字符、含运行等待词且不含向用户提问/请示拍板标记，提取保留数字的归一化文本与上一条比对：若包含迭代步数、残差等数值且数值已发生更新（如 `100 步` 推进至 `500 步`），判定为真实阶段进展并重置计数为 `1`；仅当连续 3 次内容同质无数值进展时返回 `{"decision": "continue"}` 提醒静默挂起。

### 4. 两端长会话交接（`handoff_gate.py`）

两端共用 R9 的交接原则。交接材料应包含实测进展、未尽事项和可复用的新会话提示词。两个适配器分别使用各自宿主的事件、状态和响应协议。

#### （1）反重力

反重力在有显式用户输入的主会话（`hasExplicitUserInput == true`）通过 `session_context_loader.py`、`status_guard.py` 与 `reply_repeat_guard.py` 协同处理。

1. **增量遥测与防误伤阈值**：
   - `session_context_loader.py` 统一基于紧凑版 `transcript.jsonl` 增量维护检查点列表（`checkpointSteps`）、最近 3 段检查点均值间隔、轨迹体积（`transcript.jsonl`）、`/goal` 激活标记及多模态图片读取数／字节总量；`PreToolUse` 对每次 `read_file` 图片访问同步累加去重计数。
   - **Stage-1（`advisory`，零阻断预警）**：压缩达 `11` 次、紧凑轨迹达 `4 MB`、`6` 次压缩后均值间隔 `<= 90` 步或读图达 `35` 次 / `50 MB` 时，在 `PreInvocation` 附加提醒（随检查点推进、读图里程碑跨越或新增触发源时增量提示）。
   - **Stage-2（`drain` -> `freeze`，反重力侧门禁，Codex 不套用）**：满足以下任一条件进入排空期 `drain`——用户附带 UI 历史截断提示且满足会话合理性最低门槛（防新会话首轮误杀）、压缩 `>= 16` 次、连续 3 段均值间隔 `<= 75` 步（`cp >= 10`）、轨迹 `>= 6 MiB`、读图 `>= 65` 次、读图总字节 `>= 100 MiB`，或 `cp >= 6` 且媒体步数 `>= 160`。
2. **原子排空与冻结策略**：
   - **全阶段严禁**：`invoke_subagent`、`define_subagent`、`swarm`、`schedule`、`browser_*`、`cae_harness.py` 新任务派发、`git push`、守护进程及图片 `read_file`；
   - **`drain` 排空期**：允许最多 `4` 次模型调用与 `8` 次非交接写改／测试运行／`send_message` 动作以完成手头原子单元闭环；预算耗尽自动转入 `freeze`；
   - **`freeze` 冻结期**：仅放行非图片 `read_file`、`manage_task`／`manage_subagents`、只读核对命令、交接文档写盘及本地 `git add`/`git commit`。
3. **R8 显式暂缓与 `Stop` 验收闭环**：
   - 用户新指令明确要求“暂不交接／继续当前对话”（且非“处理好交接”类措辞）时切入 `overridden` 宽限期（延后 `3` 次压缩与 `120` 步）；
   - `drain`/`freeze` 阶段在 `Stop`（`NO_TOOL_CALL` 且非 `continuationActive`）校验已落盘非空交接文档或含可粘贴新对话提示词的完整回复（开启 `/goal` 时同时强制要求包含 `<!-- GOAL_CANCELLED -->`），每回合至多阻断 1 次。

#### （2）Codex

安装器将 `handoff_gate.py --client codex` 接入以下事件。匹配 `compact`／`resume` 的 `SessionStart` 中，交接与原话恢复处理器可共用匹配组。安装器按处理器合并现有配置，重复安装时避免重复登记。宿主事件与返回字段见[Codex 钩子文档](https://learn.chatgpt.com/docs/hooks)。

| 事件 | 本仓库中的用途 |
| --- | --- |
| `PostCompact` | 登记去重后的压缩事件，作为压缩次数的计数入口 |
| `SessionStart`（`compact`／`resume`） | 恢复原话并附加交接提示，同一次压缩由 `PostCompact` 登记 |
| `UserPromptSubmit` | 识别明确交接指令（如 `/handoff` 或“请整理交接并停机”）及继续当前对话的指令 |
| `PreToolUse` | 严格模式按收口阶段检查宿主送达的工具调用 |
| `Stop` | 严格模式校验交接，必要时要求补齐材料或结束当前回合 |

默认 `advisory` 只记录信号并按条件提醒。`off` 关闭交接钩子。`enforce` 须在明确触发策略和目标宿主受控验证后启用。压缩阈值由 `--codex-handoff-compactions N` 显式设置，`0` 关闭按次数强停。阈值是用户指定的工作流策略，次数只能描述已登记的压缩事件。轨迹格式未知时按回合保守去重，可能少计。主会话身份无法确认时跳过强制处理。

在严格模式下，达到已配置的正数阈值或收到明确交接指令时进入 `drain`。允许 4 次计入预算的业务动作以完成局部收尾，随后进入 `freeze`。冻结期内钩子可放行核对、在项目内用 `apply_patch` 写入符合交接命名规则的文档及本地 `git add`／`git commit`。明确继续当前对话的用户指令可获得 3 个新压缩事件的宽限。

`Stop` 校验最终回复是否包含进展、Git 或工作区状态、未尽事项及可复制的新会话提示词。返回 `{"decision":"block","reason":"…"}` 时请求模型补齐材料，最多补正 1 次。补正后仍缺材料时提示交接未完成，并以 `continue:false` 结束当前回合。交接证据的实质核对仍由总控负责，目标与已启动后台任务由 Codex 自身的控制能力管理。

离线适配测试覆盖模拟事件和响应，宿主钩子列表加载通过亦不代表已获信任批准或已真实触发。新增钩子可能处于 `untrusted` 状态。实际宿主的信任审批、事件送达和控制结果须分别记录，不能用配置存在代替运行证据。

### Codex 实机验收记录（2026-11-13）

基于 `v1.5.0` 源码，在 Windows 的 Codex CLI `0.167.0-alpha.4.1` 上，通过本机 app-server、真实模型请求和独立临时工作区完成以下验收。测试会话使用低推理挡位；原始宿主通知、会话轨迹和状态快照保留在本机，公开仓库仅记录脱敏结论。

| 验收项 | 实测结果 |
| --- | --- |
| 已信任的生产 `advisory` 钩子 | 五类事件、六个处理器实际触发；16 条钩子完成通知均成功，3 次终端读取退出码为 `0`。手动压缩计数从 `0` 增至 `1`，后续恢复与跨进程续接不重复计数；提醒后工具操作和回合结束正常 |
| 宿主自动压缩入口 | 仅在测试会话设置 `model_auto_compact_token_limit = 1000`、计数范围 `body_after_prefix`，用合成上下文触发宿主自动压缩，未调用手动压缩接口。原生压缩记录、`PostCompact` 和 `SessionStart(compact)` 均出现，计数增加一次，后续读取成功 |
| 隔离 `enforce` 的工具控制 | 经批准，只在测试进程中信任严格模式定义，使用独立状态目录。`drain` 拦截无远端临时仓库的推送尝试；4 次独立收尾命令耗尽预算后进入 `freeze`。随后普通命令和普通源码补丁被拒绝，真实 `apply_patch` 交接文档写入及只读核对获准执行 |
| `Stop` 完整与不完整分支 | 两组真实会话均先要求一次补正，再结束回合。补齐交接时登记交接结构；仍不完整时明确报告未通过，未登记为完成，也未无限续跑 |

生产配置保持 `advisory`，未持久化严格模式的钩子信任。宿主在写入测试中自动添加的临时项目信任项已清除。以上结论限于所列版本、入口及测试场景，不代表全部模型与操作系统组合的验证；低阈值自动压缩仅验证事件链，不代表模型全窗口压力；`Stop` 结束当前回合亦不代表已取消目标循环或终止后台任务。

## 三、 全平台 UTF-8 标准流与原子写盘规约

1. **跨平台标准流 UTF-8 编码配置**：在 Windows 无终端管道及 Linux 容器 `LANG=C` 环境下，带 `-I`（隔离模式）启动的 Python 子进程可能退化为本地 ANSI/ASCII 编码。所有钩子统一通过命令行 `-X utf8 -I -B` 与模块入口 `reconfigure(encoding="utf-8", errors="replace")` 显式设置标准流为 UTF-8 编码。
2. **原子状态落盘**。JSON 状态和原话归档写入同目录临时文件，经 `flush()` 与 `os.fsync()` 后调用 `os.replace()`。Windows 下对瞬态 `PermissionError` 做有界重试。该流程缩短读到部分写入结果的窗口，并依赖目标文件系统的替换语义。
