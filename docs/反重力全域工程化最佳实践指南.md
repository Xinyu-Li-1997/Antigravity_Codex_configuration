# 反重力与 Codex 工程及科研协作实践指南

本文说明 `user-guard` 与共享技能 `cae-harness` 在日常科研与工程项目中的主控分工、模型与上下文调度、额度熔断回退、目录边界以及 Windows／WSL 协同方法。命令行参数速查见[技能说明](../template/user-guard/skills/cae-harness/SKILL.md)，安装方式见[仓库总 README](../README.md)。

## 一、主控分工与任务单规范

| 项目类型 | 默认总控 | 协作方式 |
| --- | --- | --- |
| 科研课题与综合数值工程（默认推荐） | 反重力（推荐 `Gemini 4 Carbon (High)`） | 反重力负责全局推进、长文献与多模块梳理、方向把关及文字表达；遇到数学公式推导、高阶离散格式分析与核心求解器编码时，按需调 Codex（`Astra`／`Sol`）攻坚 |
| 用户显式指定的纯代码重构／工程项目 | Codex | Codex 负责代码修改与本地测试，按需调反重力做方案复核、技术文档润色或独立验收 |

无论哪一端任总控，跨端调用都运行在独立的无头 CLI 子进程中，**看不到桌面聊天窗口里的上下文和插件面板**。因此派工任务单必须一次性写清五件事：
1. 用户最新拍板的物理假设、符号约定或工程约束；
2. 当前 Git 基线与项目根目录；
3. 需要读取的输入文件清单；
4. 允许修改的文件范围（只读任务明确写明禁止改文件）；
5. 明确的交付格式或验收命令（如单元测试、守恒残差检查、网格收敛阶验证脚本）。

子任务返回后，总控必须亲自核对原文件行号、公式步骤与命令输出，确认无误后再整合交付。

## 二、主会话、原生子代理与跨端 CLI 的选模选挡配合

1. **主会话与本侧原生子代理（最大化可用上下文）**：
   - 前端交互主会话始终保持用户自己选定的模型与挡位。
   - 在反重力中使用单模型 `Gemini 4 Carbon (High)` 作主控时，不仅主会话耐用度高，通过 `invoke_subagent` 派发的 `readonly-reader`、`readonly-auditor`、`readonly-collaborator`（默认 `model: inherit`）也会各自获得独立的纯 `Carbon (High)` 大上下文窗口（API 标称约 `1M` token），适合把长文档摘录和大文件初审分流出去，保护主会话上下文不被撑爆。
2. **跨端调用 Codex 的专长选模、最高挡位与最长上下文**：
   - **数学推导与方法论证（`math`／`direction`）**：`cae-harness` 自动优选深度推理模型 **`Astra`**（如 `gpt-6-astra`），启用单模型最高纯思考挡 **`max`**。
   - **核心数值代码、全量审计与门禁闭环（`code`／`audit`／`gate`）**：自动优选最新代工程主力 **`Sol`**（如 `gpt-6.1-sol`；支持 `--engine codex:sol` 或 `codex:astra` 显式指定）。只要任务含数学公式、守恒律、黎曼求解器、DGSEM／WENO、雅可比、牛顿法等高复杂度数值特征，或显式传入 `--tier max`，一律启用单模型最高挡 **`max`**；普通模块编码默认用 `high` 挡。
   - **最长声明上下文窗口**：脚本读取最终选定模型在本侧目录中的 `max_context_window`（当前 Codex 目录声明为 `872,000` token），在启动 `codex exec` 时显式传入 `-c model_context_window=872000`；若缺少最大值声明则采用该模型默认窗口，绝不拿其他模型的窗口上限乱套。
   - **默认禁用 `ultra` 防套娃**：后台 CLI 子任务默认排除会自动二次派生子代理的 `ultra` 挡及固定复合模式，防止多层嵌套委派快速耗尽额度。

## 三、额度熔断与本侧无缝接管

跨端调用使用各自客户端的官方登录态与额度池。遇到对侧用量触顶时，按以下机制平稳过渡：

1. **即时熔断与冷却持久化**：一旦某一方返回额度耗尽错误，`cae-harness` 立即终止同批次对该端的后续请求，返回 `quota_exhausted`（退出码 `5`），并把解析出的恢复时间写入本侧缓存（按 `windows`／`posix` 执行侧分别记录）。冷却期内再次请求会在启动 CLI 前直接拦截（`preflight_blocked: true`），避免反复白等。
2. **反重力调 Codex 时的自动回退（`--fallback-on-quota`）**：
   - 发起 `task`、`gate` 或 `audit` 时附带 `--fallback-on-quota`，若 Codex 在预检拦截或运行启动阶段触发额度熔断，且工作区文件没有任何改动，脚本会自动切回反重力本侧（`agy:default`），按同一任务性质匹配反重力最合适的模型与最高可用挡位（如 `gemini-4-carbon-high`）及本侧最大可用上下文继续完成，并在输出 JSON 的 `quota_fallback` 字段完整记录切换前后的引擎与冷却时间。
   - 若子任务在修改了部分工作区文件后才触发额度中断，脚本**绝不自动换端重跑写入**，而是保留现场差异并如实返回 `quota_exhausted` 交总控裁处。
3. **人工确认重试**：未启用 `--fallback-on-quota` 时，总控应提示用户选择改由本侧直接完成，或在充值／额度恢复后加 `--retry-quota` 发起重试（重试成功且无新熔断后自动清除旧冷却记录）。

## 四、大输入审计预算与耦合问题复核

- **估算预算与单次／分片策略**：源码体积只是上下文的一部分，系统提示词、文件清单、JSON Schema、工具调用与推理链同样占用窗口。`audit` 命令默认在模型有效窗口与压缩阈值之内留出安全余量，`single-pass` 在预算内一次送审，`sharded` 在超预算时按目录内聚性自动分片。
- **跨分片强耦合复核**：数值求解器的守恒性与稳定性往往横跨多个源文件（例如间断伽辽金谱元法 DGSEM 的体积分算子、单元界面数值通量与弯曲网格离散度量恒等式）。分片审查只能证明各片局部情况，总控必须把跨片接口、全局常数与边界通量符号拿出来做联合核对。

## 五、项目目录硬边界与验收红线

1. **双端目录硬边界（R4）**：
   - 除用户明确批准外，严禁在当前项目根目录之外的业务目录或宿主机全局配置中创建、修改、移动或删除文件（含禁止在项目外建 `.codex-worktrees` 或 `git worktree`）。
   - 反重力侧由 `status_guard.py` 解析工具参数、Python AST 与 Shell 子句：交互会话遇到越界动作弹出 `force_ask` 审批框（列明意图、动作、外部路径与命令片段），无头子任务（`CAE_HARNESS_DEPTH=1`）直接 `deny` 拒绝。
   - Codex 侧默认配置 `workspace-write` 工作区沙箱，`cae-harness` 还在任务前后做全目录文件快照对比，任何未在 `--write-scope` 授权内的改动都会报 `scope_violation`。
2. **数值与工程验收红线（R3.6）**：
   - 编译通过、单元测试绿灯、离散守恒残差达标、网格／时间步收敛阶达标分属不同证据层级，不能混为一谈。严禁为了凑过门禁擅自放宽 `rtol`／`atol`、删改断言或硬编码特例。

## 六、Windows 与 WSL 跨子系统协同及常见排障

1. **路径与会话隔离**：
   - 反重力调 Codex 采用 `codex exec --ephemeral`，不往 Codex 桌面侧边栏留垃圾会话；Codex 调反重力采用 `agy` 独立无头目录 `~/.gemini/antigravity-cli`，同样与反重力桌面聊天隔离。
   - Windows 与 WSL 各自维护独立的用户目录、登录态与额度缓存，仓库升级后在两侧分别执行安装脚本即可保持同源同步。
2. **WSL <-> Windows 互操作规则**：
   - WSL 优先调用本侧已登录的原生 CLI；若 WSL 未安装或未登录对应 CLI，在具备互操作条件时会自动回退调用 Windows 侧 `.exe`。
   - 用 Windows CLI 处理 `/mnt/<盘符>/...` 下的共享项目时可直接读写；处理 WSL 纯 Linux 路径（如 `/home/...`）时，只读任务会自动建立临时镜像目录完成审查，代码写入任务则需放在 `/mnt/<盘符>` 共享目录或使用已登录的 WSL 原生 CLI。
3. **Windows 下 Codex 沙箱反向调 `agy.exe` 的权限要求**：
   - 反重力主会话直接启动 `codex.exe` 时拥有正常宿主运行环境；但若从 Windows 版 Codex 的受限沙箱（如 `workspace-write`／AppContainer）内部反向调用 `agy.exe`，受限令牌会阻止 `agy.exe` 写入 `~/.gemini/antigravity-cli` 状态锁，表现为无 `init` 事件直至超时。此时需在放行 `~/.gemini` 写权限的宿主通道下执行，并给足 `--timeout`（建议 `>= 300` 秒）。
