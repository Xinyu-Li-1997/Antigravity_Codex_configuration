# Antigravity `user-guard` 架构设计与生命周期钩子规范

> **文档定位**：`user-guard` 与 Codex 统一生命周期钩子（Lifecycle Hooks）底层协议契约、确定性状态机与防误伤算法规范。  
> **适用范围**：Google Antigravity 2.0 App／IDE／`agy` CLI，以及 OpenAI Codex 桌面端／`codex` CLI。独立工作流与双端部署流程见[仓库说明](../README.md)与[协作实践指南](反重力全域工程化最佳实践指南.md)。

---

## 一、 Antigravity 钩子契约与编排总览

Antigravity 原生插件严格从插件根目录加载 `hooks.json`（不支持子目录 `hooks/hooks.json` 自动提升）。宿主仅支持同步命令行钩子（`type: "command"`），在进程工作目录固定为插件根目录的前提下，通过 `stdin` 传入 **camelCase**（protojson）格式载荷，并从 `stdout` 读取单行 JSON 响应。

插件运行时，宿主自动向钩子子进程注入两个关键环境变量：
- `PLUGIN_ROOT`：插件代码安装目录（如 `~/.gemini/config/plugins/user-guard`）；
- `PLUGIN_DATA`：插件专属持久化运行数据目录（如 `~/.gemini/antigravity/plugin_data/user-guard`）。

`user-guard` 优先将所有运行态状态文件（`state/`）与诊断日志（`logs/`）写入 `PLUGIN_DATA`，确保插件代码目录保持只读纯净、升级重装互不干扰。

### `hooks.json` 标准编排结构

```json
{
  "user-guard-lifecycle": {
    "SessionStart": [
      {
        "type": "command",
        "command": "python3 -X utf8 -I -B ./hooks/session_context_loader.py --event SessionStart",
        "timeout": 30
      }
    ],
    "PreInvocation": [
      {
        "type": "command",
        "command": "python3 -X utf8 -I -B ./hooks/session_context_loader.py --event PreInvocation",
        "timeout": 30
      }
    ],
    "PreToolUse": [
      {
        "matcher": "run_command|read_file|manage_task|write_file|edit_file",
        "hooks": [
          {
            "type": "command",
            "command": "python3 -X utf8 -I -B ./hooks/status_guard.py",
            "timeout": 15
          }
        ]
      }
    ],
    "Stop": [
      {
        "type": "command",
        "command": "python3 -X utf8 -I -B ./hooks/reply_repeat_guard.py",
        "timeout": 15
      }
    ]
  }
}
```

> **跨平台命令自适应**：`install.py` 在部署时会根据目标操作系统环境自动探测可用解释器（Windows 下优先探测 `python.exe` / `python` / `py -3`，Linux/macOS 下优先探测 `python3`），重写为对应平台的精确命令前缀。

## 二、 核心守护模块算法规范

### 1. 上下文压缩增量原话回溯 (`session_context_loader.py` + `user_words.py`)

#### （1）宿主事件机理与设计依据
不同于部分命令行工具在压缩后重新触发 `SessionStart`，Antigravity 的 `SessionStart` **仅在新建对话启动或会话进程冷重载时触发**；当会话运行中途发生自动上下文压缩或用户输入 `/compact` 时，宿主仅向 `transcript.jsonl` 追加一条 `"type": "CHECKPOINT"` 步骤，并在下一轮调用模型前触发 `PreInvocation`。此外，通过 `injectSteps` 注入的 `systemMessage` 会持久化保留在对话轨迹中，直至下一次压缩截断。

#### （2）二进制字节游标增量状态机 (`<convId>_compaction.json`)
为严格兑现 **“仅在发生压缩后回读注入 1 次，日常交互零全盘读取、零重复注入”**，引擎维护如下增量状态：
- `scannedByteOffset`：上次已扫描到的 `transcript.jsonl` 字节偏移量；
- `latestCheckpointStep`：已观测到的最大 `CHECKPOINT` 步骤号（初始为 `-1`）；
- `lastInjectedCheckpointStep`：已完成原话注入的最大 `CHECKPOINT` 步骤号（初始为 `-1`）；
- `hasExplicitUserInput`：当前会话是否包含人类显式输入（自动排除纯子代理会话）。

每次触发时，仅以二进制模式 `seek(scannedByteOffset)` 扫描新增尾部字节：
1. **未压缩日常轮次**（`latestCheckpointStep == -1`）：毫秒级更新游标并返回 `{"injectSteps": []}`；
2. **首次或新一轮压缩发生后首轮**（`latestCheckpointStep > lastInjectedCheckpointStep`）：
   - 单次线性解析 `transcript.jsonl`，若存在 `truncated_fields: ["content"]` 则通过单遍哈希表按需从 `transcript_full.jsonl` 补全（时间复杂度严格为 `O(N + M)`）；
   - 使用外层标签边界定位（首 `<USER_REQUEST>` 配对元数据块前的末 `</USER_REQUEST>`）及紧随 `ask_question` 的 `GENERIC` 步骤解析，完整提取用户打字原话与交互选项回答；
   - 原子落盘完整档案 `<PLUGIN_DATA>/state/<convId>_user_words.md`；
   - 按预算上限（总长 `8000` 字符、单条 `1200` 字符，超限时必保首轮立项总纲与最近定论轮次）构造含归档文件绝对路径指针的 `systemMessage` 注入，并将 `lastInjectedCheckpointStep` 更新为 `latestCheckpointStep`；
3. **压缩后的后续日常轮次**（`latestCheckpointStep == lastInjectedCheckpointStep`）：直接返回 `{"injectSteps": []}`，杜绝重复注入。

#### （3）Codex 侧多段 Rollout 压缩／恢复回溯模式（`--client codex`）
Codex 在触发上下文压缩或恢复会话时，向 `~/.codex/hooks.json` 中匹配 `^(compact|resume)$` 的 `SessionStart` 钩子传入 `session_id` 与当前 `transcript_path`（位于 `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`）。同一逻辑会话在多次续跑或归档后可能跨越多个 `rollout-*.jsonl` 分段（含 `archived_sessions/`）：
1. 引擎首先校验首行 `session_meta`（排除 `subagent` 子代理会话），自动扫描合并同 `session_id` 的全部主会话分段；
2. 优先依据 `internal_chat_message_metadata_passthrough` 中的 `provenance.type` 过滤 `harness`／`agents_md` 系统注入块，保留人类输入与 `<send_user_message_question_reply>` 选项框回答，跨分段按稳定记录 ID 去重（绝不按纯文本去重）；
3. 原子写入 `~/.codex/hooks/state/user-words/<session_id>.md` 与 SHA-256 校验清单（若遇读取缺口且存在上次已验证文档则保留旧档并如实标注缺口），通过 `hookSpecificOutput.additionalContext` 返回归档路径与预算内核心原话摘要。

### 2. `PreToolUse` 项目目录硬边界与防空转轮询门禁 (`status_guard.py`)

#### （0）项目目录外文件改动硬边界门禁（R4 硬约束）
针对 `write_file`、`edit_file` 与 `run_command`，门禁从 `workspacePaths`（回退 `cwd`）构建当前会话允许写入的项目根目录集合，并精确区分运行时记忆缓存与外部业务路径：
- **自动放行的合法运行时区域**：当前项目根目录（含 `<盘符>:/...` 与 `/mnt/<盘符>/...` 跨端挂载等价路径）、系统标准临时目录（`/tmp`、`%TEMP%`）、宿主与项目关联的对话记忆／子代理轨迹／制品草稿目录（`~/.gemini/antigravity/{brain,plugin_data,conversations,scratch,...}`、`~/.codex/{memories,sessions,cache,tmp,...}`）以及标准工具缓存区（`~/.cache/...`），同时对本地可达路径执行 `Path.resolve()` 防御软链接／目录联接越界逃逸；
- **AST 与子句命令头精确配对（零只读误报）**：对 `python -c`／here-string／heredoc 内联脚本使用 Python `ast` 语法树解析，仅拦截真实落盘／删改调用（如带 `'w'|'a'|'x'|'+'` 的 `open`、`.write_text`、`os.remove`、`shutil.rmtree`、`shutil.copy*` 目标端等），彻底忽略只读 `open`、内存数组 `.copy()`、`.md` 文件名、数值比较 `>` 以及被调用的外部虚拟环境解释器路径；外层 Shell 先剥离 `wsl`／`bash -lc`／`powershell -Command` 包装，再按子句命令头严格配对写删动词与输出目标；
- **真实越界处置与结构化可读提示**：检测到向项目外业务目录执行写删、创建外部 `git worktree`（如 `../.codex-worktrees`）或改写全局核心配置（如 `~/.gemini/config`、`~/.codex/config.toml`）时：
  - **交互主会话**（未设置 `CAE_HARNESS_DEPTH=1`）：返回 `{"decision": "force_ask", "reason": "..."}`，在 UI 弹窗按四要素清晰列出**当前任务意图（`toolSummary`）、具体写删动作、项目外目标路径与触发语句片段**，交由用户一目了然地审阅批准；
  - **跨端无头子任务**（`CAE_HARNESS_DEPTH=1`）：直接返回 `{"decision": "deny", "reason": "..."}` 硬阻断（即使 CLI 附带 `--dangerously-skip-permissions` 亦由钩子优先拦截）。

#### （1）严格锚定的证据文件识别
仅对以下目标启用指纹守卫，严禁误伤项目普通源码与业务 JSON 配置（如 `http_status.json`、`test_result.json`）：
- 扩展名属于 `.log`、`.out`、`.err`、`.output`；
- 文件名严格匹配锚定正则：`^(?:journal[^.]*\.jsonl|output\.[^.]+|task[-_]?output[^.]*(?:\.[^.]+)?|results?(?:\.(?:txt|json|jsonl|dat|csv))?|task\.(?:json|txt|status)|wf_[^.]+\.json)$`；
- 路径位于 `.system_generated/tasks/` 或 `.system_generated/steps/` 下（显式豁免插件自身的 `state/` 与 `logs/` 目录）。

#### （2）查询参数签名与快速复合指纹
- **查询键构造**：
  - `read_file`：`read_file:<canonical_path>|s=<StartLine>:e=<EndLine>:b=<ByteOffset>` —— 保证大文件分段翻页读取（如 `#L1-800` 翻至 `#L801-1600`）因参数变化 100% 放行，仅拦截同一页无变化重复读取；
  - `run_command`：剥离 `wsl`、`bash -c`、`powershell -Command`、`env`、`timeout` 等前导包装器后识别只读命令，键为 `run_command:<canonical_path>|<normalized_command>` —— 保证先 `grep` 后 `tail` 变参放行，同参原地轮询拦截；
  - `manage_task(Action="status")`：自动定位 `<brain>/<convId>/.system_generated/tasks/<TaskId>.log`，直接比对该后台任务日志文件的物理指纹 —— 任务产生新日志输出即刻恢复 `allow`，无日志文件时采用 `30s` 冷却窗口防高频轮询且绝不永久锁死。
- **跨子系统不可达路径豁免**：在 Windows 宿主下通过 `wsl` / `ssh` / `docker` 查看子系统内部宿主机不可见路径（如 `/home/.../run.log`）时自动放行，防止 `non_existent` 假指纹锁死。
- **复合文件指纹（防 GB 级算例日志超时）**：
  $$\text{Fingerprint} = \begin{cases} (\text{mtime\_ns},\ \text{size},\ \text{SHA256}_{\text{full}}), & \text{size} \le 4\ \text{MB} \\ (\text{mtime\_ns},\ \text{size},\ \text{SHA256}_{\text{head 1MB} \parallel \text{tail 1MB}}), & \text{size} > 4\ \text{MB} \end{cases}$$

### 3. `Stop` 防同质等待刷屏门禁 (`reply_repeat_guard.py`)

- **防死循环双保险**：
  1. 检查官方 `payload.get("continuationActive")`：若为 `true`（本轮已处于 `Stop` 钩子触发的强制续跑中），无条件返回 `{"decision": "allow"}`；
  2. 记录已拦截的归一化签名列表 `blockedSignatures`，同一签名在单回合内最多阻断 1 次。
- **保留数值进展的同质性判据**：
  - 仅从 `transcript.jsonl` 尾部 `256 KB` 窗口逆序定位最近一条 `USER_INPUT`（或子代理父消息）后的最新模型回复；
  - 若回复长度 `<= 300` 字符、含运行等待词且不含向用户提问/请示拍板标记，提取保留数字的归一化文本与上一条比对：若包含迭代步数、残差等数值且数值已发生更新（如 `100 步` 推进至 `500 步`），判定为真实阶段进展并重置计数为 `1`；仅当连续 3 次内容同质无数值进展时返回 `{"decision": "continue"}` 提醒静默挂起。

## 三、 全平台 UTF-8 标准流与原子写盘规约

1. **全平台编码自愈**：在 Windows 无终端管道及 Linux 容器 `LANG=C` 环境下，带 `-I`（隔离模式）启动的 Python 子进程可能退化为本地 ANSI/ASCII 编码。所有钩子统一通过命令行 `-X utf8 -I -B` 与模块入口全平台 `reconfigure(encoding="utf-8", errors="replace")` 双重锁定 UTF-8。
2. **原子状态落盘**：所有 JSON 状态文件与原话 Markdown 归档统一经由同目录 `.tmp.<pid>` 临时文件写入、`flush()` + `os.fsync()` 后调用 `os.replace()` 原子替换，确保异常中断或并发触发时状态文件零损坏。
